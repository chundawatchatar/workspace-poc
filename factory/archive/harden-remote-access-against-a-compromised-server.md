## Harden remote access against a compromised server

The host is the root of trust: it will become an installable app while the client stays a plain web app, so a compromised server could relay, phish approvals or serve modified client code. This sprint closes the small holes, moves approval and oversight onto the host, and makes the tunnel recover faster. Per-device scopes, a machine key pair instead of the raw `hello` secret, end-to-end encryption (REM-2), separate client hosting and signed host updates come in later sprints.

- [x] Server: read `SERVER_MAX_CHANNELS` with `requiredEnv` instead of the `|| 128` default in `apps/server/src/index.ts`, add it to `.env.example`, and check the server's other `process.env` reads for code defaults the same way → 058-server-env-defaults
- [x] Host: manage devices from the terminal with `bun run host:remote devices` (list approved and pending devices by fingerprint and age), `devices approve <fingerprint>` (asks y/N, `--yes` for scripts) and `devices remove <fingerprint>`, and show the pending count in `status`; it goes through the running host's local-only route when the host is up and writes `.data/devices.json` when it is stopped, like `link`; never prints a public key or nonce; update `docs/remote-access.md` and REM-5 → 059-host-remote-devices-cli
- [x] Host: approve a device only by typing the fingerprint its own browser shows (in the Remote access setting and in `host:remote devices approve`), instead of an Approve button on each pending row, so a device the server pushed into the pending list can't be approved by a mis-click; a typed fingerprint that matches no pending device gets one clear error; update the risks in `docs/architecture.md` → 060-typed-fingerprint-approval
- [x] Host: through the tunnel, accept an access key from a connect link only together with a fresh proof from an approved device, as for relay tickets (local requests keep accepting the key alone); the client sends its device proof with key access too, and an unapproved browser sees the same unapproved hint with its fingerprint; update `docs/architecture.md` and REM-5 → 061-tunnel-key-device-proof
- [x] Server and host: when a user's session is revoked or they sign out everywhere, the server sends a tunnel control frame to each of that account's online machines, and the host closes the sockets opened with that account's tickets; the frame names only the account, and the host still decides alone; remove the risk from `docs/architecture.md` and `docs/remote-access.md` → 062-revoke-closes-tunnel-sockets
- [x] Host: list live remote sessions in the Remote access setting (device fingerprint, account or access key, open sockets, started at), refreshed live, with an End button per device that closes its sockets, and a `host:remote sessions` command that prints the same; local only, refused through the tunnel → 063-remote-sessions-list
- [x] Host: keep a local audit log of remote access in `apps/host/.data/remote-audit.jsonl` (device fingerprint, account or key id, opened and closed times, refused attempts with a fixed reason), capped in size, never logging a ticket, proof, key, path or command; show the last entries in the Remote access setting and with `host:remote log` → 064-remote-audit-log
- [x] Host: notify the local user when a new device asks for approval, through the local page's notification setting (the same one agents use) and a line in the host log, naming only the fingerprint and when it asked → 065-device-approval-notify
- [x] Host: reconnect the tunnel within about a second after the machine wakes from sleep or the network changes, by spotting a jump in timer time or a missed pong instead of waiting out the 45-second silence timeout, without dropping the backoff after repeated failures; test with fake timers → 066-tunnel-fast-reconnect
- [x] Host and client: the host sends a "remote access off" frame before closing its tunnel when the user turns remote access off, the server keeps that state for the machine, and the home page shows "Remote access off" instead of "Offline"; update REM-4, and mark REM-3 Done in `docs/REQUIREMENTS.md`, since the host already connects outwards → 067-remote-access-off-state
