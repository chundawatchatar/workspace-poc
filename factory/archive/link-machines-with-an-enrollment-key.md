## Link machines with an enrollment key

The signed-in user creates a one-time enrollment key in the client and gives it to the host, which links the machine to that account. Before linking, the host shows the user three things to confirm: the server address (from the host's own config only, never from the key), the account the key belongs to, and the key's fingerprint. Access model for now: any browser signed in to the owning account can open the machine, so the server is trusted to say who is signed in (accepted risk, recorded in the docs, until per-device approval and end-to-end encryption).

- [x] Server: add enrollment keys: a `machineEnrollments` table (`userId`, key hash, `createdAt`, `expiresAt`, `usedAt`) registered in `scopedTables`, an `auth: 'user'` `serverRoutes.machines` endpoint that creates a single-use key valid for 15 minutes and answers it once with its fingerprint (last 4 characters) and expiry, and tunnel control frames that let a connected machine preview a key (answers the account's name and masked email, the fingerprint and expiry, without using it) and redeem it (marks it used and links the proven machine id to that account); unknown, used and expired keys get one error, and preview and redeem are rate-limited per machine → 051-enrollment-keys
- [x] Client: add "Connect a machine" to the home page, which creates an enrollment key and shows it once with a Copy button, its fingerprint, a countdown to expiry and the `bun run host:remote link <key>` command, and shows the machine in the list as soon as it links → 052-connect-a-machine
- [x] Host: link with an enrollment key from a "Link key" field in the Remote access dialog; the server address comes only from `SERVER_URL`, the saved setting or a built-in default; the host previews the key, shows the server address (warning when it isn't the default), the account and the key fingerprint, and redeems only after the user confirms; it saves the linked account in `.data/` and shows it in the dialog with an Unlink button → 053-host-link-key
- [x] Host: configure remote access from the terminal with `bun run host:remote`: `status` (server address, tunnel state, linked account), `server <url>` (save the server address, `wss://` only except loopback), `link <key>` (the same preview and three-value check as the dialog, confirmed with y/N, or `--yes` for scripted setups, which still prints all three), `unlink`, and `on`/`off`; each command goes through the running host's local-only route when the host is up and writes `.data/` directly when it is stopped, like `host:rotate-key`, and prints no key or secret beyond the fingerprint → 054-host-remote-cli
- [x] Open a linked machine from any browser signed in to its account: the server relays requests for the owning account's signed-in users with the account as the principal, the host accepts them only for its linked account and keeps accepting access keys from connect links, and the home page's Open link no longer needs a key saved in the browser → 055-account-open-machine
- [x] Remove the pending machine link (`pendingLink.ts`, `sendPendingMachineLink` and the link-by-id endpoint) now that enrollment keys link machines, and update `docs/accounts.md`, `docs/remote-access.md`, `docs/architecture.md` (the server is trusted for access until device approval) and `docs/REQUIREMENTS.md` (REM-1, REM-4) → 056-remove-pending-link
- [x] Device approval: a browser holds a non-exportable key pair (WebCrypto or WebAuthn) whose public key the host approves once, and the host then accepts account access only with a signature from an approved device key, so a compromised server can no longer open linked machines; update `docs/architecture.md` and `docs/REQUIREMENTS.md` → 057-device-approval
