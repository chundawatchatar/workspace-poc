## End-to-end encryption between browser and machine

REM-2: the server keeps relaying, but can no longer read or inject into what an approved browser and its machine send each other, and can't pose as the machine. Builds on the previous section (approval by typed fingerprint, device proofs for key access). Each side proves itself with a key the other already trusts: the browser with its approved device key, the machine with a machine key the browser pinned without trusting the server. Nothing is deployed yet, so machines may relink once instead of carrying a migration. Modified client code from a compromised server is still out of scope (the client can't be installed); the host's sessions, audit log and kill switch cover it.

- [x] Host and server: give each machine an Ed25519 machine key (created once in `apps/host/.data/`, mode 0600, never sent or logged) and replace the raw secret in `hello` with a signature over a fresh server challenge; the machine id becomes a hash of the public key, the server stores only the public key, and the tunnel protocol version goes up; existing machines relink once, as documented in `docs/remote-access.md` → 068-machine-key-hello
- [x] Host and client: let the browser pin the machine's public key without trusting the server: a connect link carries the key's fingerprint in its fragment, and for account access the browser shows the machine fingerprint once after approval and pins it only when the user confirms it matches the one the host's Remote access setting and `host:remote status` show; a pinned key is kept per machine in IndexedDB beside the device key, and a mismatch later stops the connection with a clear warning instead of reconnecting → 069-pin-machine-key
- [x] Shared: add the end-to-end crypto in `packages/shared/src/contracts/e2e.ts`, with no wiring yet: a handshake where each side sends an ephemeral P-256 ECDH key signed by its long-term key (the browser's device key, the machine key), HKDF over the shared secret and both transcripts into separate AES-GCM keys per direction, and seal/open with a per-direction counter that refuses replays, reordering and a counter that would wrap; WebCrypto only, the same code in Bun and the browser, tested with fixed vectors and tampering cases → 070-e2e-crypto
- [x] Host and client: open an end-to-end session before any remote request: `createRemoteTransport` runs the handshake through the relay, the host verifies the device is approved and answers signed with the machine key, the browser checks it against the pinned key, and the host keeps sessions in memory only, expiring with the device's tickets and closed when the device is removed or ends; no request is sealed yet → 071-e2e-session-handshake
- [x] Host, server and client: seal HTTP through the tunnel with the sealed frame type planned in `docs/architecture.md`: the browser seals method, path, headers and body into one opaque payload, the server routes it on the envelope only, and the host opens it, serves it and seals the response head and each body chunk, so streaming still works; `auth.failed` and other control frames stay outside the seal → 072-e2e-seal-http
- [x] Host, server and client: seal WebSocket channels the same way: each `ws.open` carries its path and auth message sealed, every `ws.data` payload is sealed with that channel's counter, and flow control (`ws.ack`) keeps counting sealed bytes; terminals, the events socket and agent state work unchanged in the page → 073-e2e-seal-websocket
- [x] Host: refuse unsealed account and key traffic through the tunnel once sealing works (local requests are unchanged), and record a refused unsealed attempt in the remote audit log; update `docs/architecture.md` (the risks that remain: client code served by a compromised server, metadata such as timing, sizes and which device connects), `docs/remote-access.md`, `docs/accounts.md`, and REM-1 and REM-2 in `docs/REQUIREMENTS.md` → 074-refuse-unsealed-tunnel
