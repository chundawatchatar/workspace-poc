## Sign-up with an email code

Sign-up moves from "create the account, then click the emailed link" to "prove the inbox with a 6-digit code, then create the account". Today a sign-up stores an unverified user with whatever password was typed, so someone else can sign up with your email first: you then verify an account that has their password, and they can sign in once you do. A repeat sign-up also answers "check your inbox" but sends nothing. The new flow is two screens: (1) name, email and password, then "Send code" (the password stays in the browser's memory only; no account or password is stored yet, only the hashed code); (2) "Enter the code we sent to <email>", one request that checks the code, creates the verified account with its password and signs in. Use Better Auth's own pieces and defaults wherever they exist (the `emailOTP` plugin from `better-auth/plugins`, its `verification` table storage, `storeOTP: 'hashed'` with its built-in SHA-256, its 6-digit / 5-minute / 3-attempt defaults and its rate limits); add our own code only where Better Auth has nothing. Nothing is deployed and there is no user data to keep, so there is no recovery or migration of unverified accounts: the new flow only ever creates new, verified accounts and refuses any existing account, and a dev database is cleared with `bun run db:reset`. Run the two items in order: the first keeps today's flow working so `main` never breaks between them, without preserving the data that flow creates.

- [x] Server: add sign-up by email code next to the current flow (`apps/server/src/modules/auth/`). Add Better Auth's `emailOTP` plugin with `storeOTP: 'hashed'` and its default length, expiry, attempts and rate limits. Its `sendVerificationOTP` sends through the mailer: a new `signUpCode` template with the code when the address has no account, and a new `accountExists` template ("You already have an account: sign in, or reset your password", with links to `/auth/sign-in` and `/auth/forgot-password`, no code) when it has any account, so the answer to "send code" is the same for every address. The code is always sent with the plugin's `sign-in` purpose (`send-verification-otp` with `type: 'sign-in'`): in 1.7.14 every other purpose silently sends nothing to an address with no user, and `check-verification-otp` refuses a correct code with `USER_NOT_FOUND` when no user exists and never uses the code up, so neither may be used. Add one sign-up endpoint under `/api/auth` as a small Better Auth plugin endpoint (so Better Auth's origin check, rate limits and session cookie apply; not in `serverRoutes`) that takes `name`, `email`, `password` and `code` in one request. It checks the password against Better Auth's length rules before the code is touched, then redeems the code through the plugin's own `sign-in/email-otp` step (called server-side, never exposed), which uses the code up atomically before any account write, counts wrong codes, creates the user with `emailVerified: true` and a session. Then it sets the name and saves the password as a credential account. Requirements: sign-up only ever creates a new account; it never signs in to, promotes or changes an existing one, verified or not. The plugin's `sign-in/email-otp` step signs in an existing verified user and promotes an existing unverified one (dropping its password and sessions), and the `accountExists` choice is made only when the code is sent, so the endpoint must refuse when a user with that email exists at redemption (for example because another sign-up for the same email completed first) without letting the plugin step change that user. It succeeds only when this request created the user, decided atomically so that two concurrent redemptions for one email can't both succeed (for example the email's unique constraint or a lock, never a check-then-create alone); otherwise it answers the generic refusal, saves no password, keeps no session it created and leaves the existing account unchanged. A correct code is accepted exactly once, so of several concurrent submissions with it exactly one succeeds and the rest get the generic refusal; a wrong code's attempt count is kept even when the request fails (so the code check must never run inside a transaction that a later failure rolls back); if any write after the code is redeemed fails, the request leaves no new account, credential or session behind (turn on the adapter's `transaction: true`, off by default in `drizzleAdapter`, for the writes that can share one, and remove a user this request created if the password write still fails), and the user asks for a new code. Every refused code gets one generic "invalid or expired code" answer. Turn off with `disabledPaths` every `emailOTP` path the client won't call (its public sign-in, `check-verification-otp`, email verification, password reset and email change by code), so only "send code" and our sign-up endpoint are reachable. Never log a code, an email address or a password. Test with the capturing mailer: new address gets a code and the endpoint creates a verified, signed-in account whose password signs in; an address with any account gets `accountExists` and no usable code; a wrong code three times locks that code, also when the requests fail; a short password doesn't use up the code; two concurrent submissions of the right code give exactly one account and one success; a code that was redeemed can't be used again; a code sent while the address had no account is refused once another sign-up has created it, and that account's password, name and sessions are unchanged; two concurrent sign-ups for the same new email with different passwords leave exactly one success, whose password is the one saved; a forced failure of the password write leaves no account, credential or session; the disabled `emailOTP` paths answer 404.
