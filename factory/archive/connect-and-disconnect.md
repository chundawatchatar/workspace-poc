## Connect and disconnect

The host's Remote access dialog becomes one form: the server address (prefilled with the default and editable), the account email and the key from the client, and a Connect button. Connect first asks to confirm what was typed. The owner then accepts or rejects the machine in the client. While the machine is connected, the fields are locked. Disconnect, which also works when the connection is broken, unlocks them. The CLI does the same with `corch connect` and `corch disconnect`. Run the jobs in order.

- [x] Remote access: Connect and Disconnect in the host's Remote access dialog and CLI. Not connected, the dialog shows Server address, Email, Key and Connect. Server address is prefilled with the address in use (the built-in default when nothing else is set) and is editable; one set by a flag or variable stays read-only with "Set by …" as now. Connect first asks to confirm the email, the server address (with today's warning when it isn't the built-in default) and the key's last 4 characters, never the whole key. On confirm, the host saves the address, starts the tunnel to it at once without a restart (so `restartNeeded` and "from its next start" go away), and redeems the key with the email. The server links only when the email matches the key's owner, ignoring case. A mismatch gets the same `invalid_key` as an unknown key, so the answer never says whether an email has an account. The host, the CLI and the server never log the key or the email, and no error message repeats them. The Preview step and `enroll.preview` go away. Connected, the dialog shows the account and the server read-only, the machine key, browser approval, the approved browsers and Disconnect. The on/off switch goes away, and a machine already linked counts as connected. Disconnect asks to confirm. When the tunnel is up, it asks the server through a new tunnel frame to remove the machine from the account's list, with the machine id from the tunnel's proof. Then it unlinks, clears the approved devices as unlinking does now, stops the tunnel and unlocks the fields. With the tunnel down, it still does all of this locally and says to remove the machine from the list in the client. CLI: `corch connect --email <email> --key <key> [--server <url>]` uses the default server when `--server` is left out. `corch disconnect` disconnects. Both confirm with `[y/N]`, take `--yes`, and need the host running. `corch status` says whether the machine is connected, and to which account and server. In dev, `bun run host:remote connect` and `bun run host:remote disconnect` take the same flags and replace `link`, `unlink`, `server`, `on` and `off`. The client's "Connect a machine" dialog shows the `corch connect` command with the signed-in email, the new key and `--server` filled in. The server returns its own tunnel address with the new key, from a new setting added to `.env.example`, so the command reaches the server that issued the key on a self-hosted deployment too.
