# AGENTS.md

Instructions for AI coding agents working in this repository. Shared by Claude Code (via `CLAUDE.md`), Codex and Gemini CLI.

## Commands

- Bun workspaces monorepo (`apps/web`, `apps/client`, `apps/site`, `apps/host`, `apps/ptyd-bun`, `apps/server`, `packages/shared`, `packages/domain`, `packages/terminal`, `packages/ui`, `packages/terminal-ui`). Use `bun`, never npm/yarn/pnpm. `bunfig.toml` hoists all dependencies into the root `node_modules`.
- `bun run dev` starts both apps: web on 127.0.0.1:3210 (strict port), host on 127.0.0.1:4599. It does not start the client.
- `bun run dev:client` starts the global app (`apps/client`) on 127.0.0.1:3220 and the cloud server (`apps/server`) on 127.0.0.1:4600, set up to talk to each other. To reach this machine through them, run `bun run dev` in another terminal with `SERVER_URL=ws://127.0.0.1:4600 CLIENT_URL=http://127.0.0.1:3220`.
- `bun run dev:site` starts the marketing site and docs (`apps/site`, Astro, static) on 127.0.0.1:3230. Its name, links and prices live in `apps/site/src/site.config.ts`; docs pages are Markdown in `apps/site/src/content/docs/`.
- `bun run db:up` starts the dev Postgres and Mailpit from `compose.yaml` (localhost-only ports; inbox on http://127.0.0.1:8025) and waits until Postgres is healthy. `bun run db:down` stops them and keeps the data. Copy `.env.example` to `.env` first.
- `bun run db:generate` writes a new migration into `packages/domain/migrations/` after you edit a schema in `packages/domain/src/schemas/`; commit it, and never hand-edit a generated migration. `bun run db:migrate` applies pending migrations to `DATABASE_URL` (run `bun run db:up` first).
- Server-side settings live in the root `.env` (gitignored; `.env.example` is the committed template). Server-side entry points, such as `apps/server` and a future `drizzle.config.ts`, call `loadRootEnv()` from `@orch/shared/env` before reading `process.env`, since Bun only auto-loads `.env` from the working directory. The shell environment wins over the file. Never load it in browser apps.
- Verify changes with `bun run typecheck` (runs `tsc` in every workspace) and `bun test`.
- Tests use Bun's built-in runner and live next to the source as `*.test.ts`. Keep them few and behavior-focused (see the `write-tests` skill). `bun run test:coverage` shows coverage.
- `bun run lint` / `bun run format` run Biome (`biome.json` at the root) on the whole repo. After editing, format only the files you changed: `bunx biome check --write <files>`.
- Silence a lint rule for one line with `// biome-ignore lint/<group>/<rule>: <reason>` (`{/* … */}` inside JSX), and always give the reason.

## Code style

- No semicolons, single quotes, 2-space indent, 120-column lines. Biome enforces this.
- `verbatimModuleSyntax` is on: import types with `import { type X }` / `import type`.
- `noUnusedLocals` and `noImplicitOverride` are on: remove unused bindings, and mark overrides with `override`.

## Architecture gotchas

- `packages/shared` holds the layout model, its reducer and the wire protocol (`protocol.ts`). It is consumed as raw TS (`exports: ./src/index.ts`), so it has no build step. Protocol changes must be made on both the host and the web side. Its one server-only helper, `loadRootEnv()`, is the subpath export `@orch/shared/env` and is never re-exported from `index.ts`, which browser code imports.
- `packages/domain` holds the cloud server's database code (Drizzle schemas, migrations, `createDomain`), consumed as raw TS. Only `apps/server` imports it, never `apps/client`, `apps/web`, `apps/host`, `packages/shared`, `packages/ui` or `packages/terminal-ui`. One table per file in `src/schemas/`. The Better Auth tables (`user`, `session`, `account`, `verification`) come from its CLI; regenerate them as `packages/domain/README.md` describes, never by hand. App code reaches the database only through `domain.forUser(principal)`, whose repositories scope every query to the principal's `userId`. `forAuthLibrary()` is for Better Auth's `drizzleAdapter` only, and `skipAuthorization(reason)` needs a real reason and is logged. Every new table with a `userId` column must be registered in `scopedTables` (`src/scoped-tables.ts`); a test fails otherwise. Tests get a migrated in-memory database from `createTestDomain()` / `createTestDb()` in `@orch/domain/testing` (PGlite, no Docker, never reads `DATABASE_URL`). `"user"` is a reserved word, so quote it in hand-written SQL.
- `packages/ui` holds the shared, presentational UI (components, themes, `styles.css`), consumed as raw TS like `packages/shared`. It is reused by a closed-source app, so components take data and callbacks as props and never import from an app (store, commands, router) or a form library. Its form fields take plain `value`/`onChange`/`onBlur`/`error` props and are styled only with theme tokens. `packages/terminal-ui` wraps them to connect its store.
- `packages/terminal-ui` holds the page inside a machine (sidebar, layout, terminals, palette, shortcuts, overlays, toasts and their store), consumed as raw TS. Its root `<TerminalUI>` takes a `HostTransport` (every request and socket goes through it) and navigation callbacks as props. Like `packages/ui`, it never imports from an app (router, app store); differences between apps come in as props, never as app checks (`isClient`, `isLocal`, …).
- `apps/web` is a thin shell: the document, the TanStack Router routes and a `<TerminalUI>` with a local transport. Page code goes in `packages/terminal-ui`.
- `apps/client` is the global app: TanStack Start in SPA mode with file-based routes in `src/routes/` (no SSR, no server functions). `apps/client/src/routeTree.gen.ts` is generated; never edit it by hand. The build prerenders only the root shell into `dist/index.html`, so `dist` is a static folder; the server bundle in `.output/` is only used to prerender it. Every inline script must be in that shell with fixed contents, since the server allows them by hash. In dev, `/api` is proxied to the cloud server (`CLIENT_API_TARGET`, default `http://127.0.0.1:4600`). The root route provides a TanStack Query client. It renders `<TerminalUI>` with `createRemoteTransport` for a machine saved in `localStorage` from a connect link (`#machine=<id>&key=<key>`), read in `getRouter()` before the router reads the URL. Who is signed in lives in `src/lib/auth.ts`: `sessionQuery` (`['session']`, through Better Auth's client, never its `useSession`), `requireSession` as the `beforeLoad` of every guarded route (it sends a signed-out user to `/auth/sign-in`; `/auth/sign-in` and `/auth/sign-up` are never guarded, their `redirect` goes through `safeRedirect`, which refuses any `/auth` path, and a signed-in visit to either leaves through `leaveIfSignedIn`), and an identity watcher that clears the whole query cache and the pending machine link whenever the user changes. Every query holding account data is keyed with `accountKey(userId, ...)` or built with `accountQuery`; `serverQuery` is for `auth: 'public'` endpoints only. Every auth page lives under the `/auth` layout route (`src/routes/auth.tsx`), which draws the product's mark, name and subtitle (`BrandMark`, `PRODUCT_NAME`, `PRODUCT_TAGLINE` from `@orch/ui`) around the page's `AuthCard`, in theme tokens only, and the layout itself is neither guarded nor left when signed in. Sign-in and sign-up also show the pitch (`PRODUCT_FACTS`, `PRODUCT_HEADLINE`, shared with the site) and `AuthWorkspacePreview` beside the card on wide screens; the email pages show the card alone. The email pages are there too: sign-up's in-page "Check your inbox" (`CheckInbox`, with a resend button), `/auth/verify-email`, `/auth/forgot-password` and `/auth/reset-password`. Of these only forgot-password uses `leaveIfSignedIn`, since a verify or reset link may be opened while signed in. Emailed links carry their token in the fragment (`/auth/verify-email#token=<t>`, built by `emailLinkUrl` on the server); `acceptEmailLinkToken` (`src/lib/emailLink.ts`) reads it in `getRouter()` and on `popstate`, before the router does, keeps it in memory only and removes it from the URL, and the page takes it once with `takeEmailLinkToken`. Never put the token in storage, a query key, a URL or a log. Forms use TanStack Form with Zod schemas (Standard Schema, no adapter; the auth schemas and form options are in `src/lib/authForms.ts`) and the `@orch/ui` fields (`TextField`, `PasswordField`, `Button`, `FormError`). It imports only `@orch/terminal-ui`, `@orch/ui`, `@orch/shared` and `better-auth/react`, never `apps/web` or `@orch/domain`.
- Both apps pass their router outlet to `<TerminalUI>` as `children`, rendering `HomeView`, `WorkspaceView` or `NotFound` from `@orch/terminal-ui`.
- Import icons from `@orch/ui/icons` (lucide-react, re-exported), never from `lucide-react` directly.
- The host is organized into feature modules (`apps/host/src/modules/<feature>/`), one responsibility per file: `.routes.ts` (HTTP), `.ws.ts` (WebSocket), `.service.ts` (logic), `.repository.ts` (persistence). Every HTTP and WebSocket route is defined once in the `routes` registry in `packages/shared/src/contracts/` (full path + Zod schemas). The host serves it, and clients call it with `callApi`/`buildSocketUrl`, so never write `/api` or `/ws` paths by hand. Follow the `host-feature-module` skill.
- The cloud server's own API (`apps/server`, under `/api` but never `/api/auth/*`, which is Better Auth's) is defined in the `serverRoutes` registry (`packages/shared/src/contracts/server.ts`, `defineServerContract`), kept apart from the host's `routes`, which the server relays under `/m/<id>`. The server serves it with `createServerRouter` (`apps/server/src/lib/`), the client calls it with `callServer`, `serverQuery` (public GET only; signed-in GETs use `accountQuery`) and `serverMutation` (non-GET only) from `apps/client/src/lib/server.ts`. An endpoint is `auth: 'user'` unless it says `auth: 'public'`, and declares its own error codes in `errors` on top of the common ones. GET never changes state; review for it, since types can't enforce it. The router refuses a non-GET without a same-site or `SERVER_TRUSTED_ORIGINS` `Origin` (403) or a JSON `Content-Type` (415) before any handler runs, and an unknown `/api` path gets the JSON `not_found`, never the client page. The session is read only through Better Auth's `auth.api.getSession` (`createAuthenticate` in `modules/auth/auth.middleware.ts`), never by reading the cookie, and only after those two checks. An `auth: 'user'` handler gets `principal` (`userId`, `email`, `name`) and `data`, the principal's scoped repositories from `forUser`, and never the `Domain`, `forAuthLibrary()` or `skipAuthorization`; `index.ts` passes `forUser` as the closure `(p) => domain.forUser(p)`. A public handler gets `null` for both.
- Better Auth owns `/api/auth/*` in `apps/server/src/modules/auth/` (`createAuth` in `auth.service.ts`, mounted by `auth.routes.ts` only when accounts are on, never through `serverRoutes`): email and password with required email verification, emails through the mailer, sessions in the database through `domain.forAuthLibrary()`. The session cookie is `Path=/api`, `HttpOnly`, `Secure`, `SameSite=Lax`, so browsers never send it to `/m/*`, and the cookie cache is off, so a revoked session ends on its next request. Users list and end their sessions with Better Auth's `list-sessions`, `revoke-session`, `revoke-other-sessions` and `revoke-sessions` (`list-sessions` needs a session younger than `freshAge`, one day); an operator signs a user out everywhere with `bun run --filter @orch/server sessions:revoke-user <email>` (`revokeUserSessions` in `auth.sessions.ts`, through `skipAuthorization`). Its rate limits are in memory and keyed by the `x-orch-client-ip` header the routes set from `clientIpReader`, never by a client's `X-Forwarded-For`. Better Auth turns off its origin check and rate limits when `NODE_ENV=test`, so `createAuth` sets both on explicitly; keep it that way. Its logger masks emails, URL paths and tokens and drops error details. A duplicate sign-up gets the same response as a new one (see `docs/architecture.md` for the remaining timing risk).
- The machines module (`apps/server/src/modules/machines/`, `serverRoutes.machines`) lists, links, renames and unlinks a user's machines through `data.machines` only. The accounts API stores machine ids and names, never access keys: its inputs are strict (a `key` field gets 400) and it never reads request headers. Online state comes from the one `MachineRegistry`, built in `index.ts` before the accounts modules. Accepted risk: the server can't prove a user holds a machine's key, so linking someone else's id only reveals whether that machine is online; the host's key check still guards all access (see `docs/architecture.md`).
- The server relays machines under `/m/<id>` on its own origin, where the account session cookie lives, so it drops `Cookie` from relayed HTTP requests and socket upgrades (`apps/server/src/lib/relay.ts`) and `Set-Cookie` from machine responses (`forward.service.ts`). These are filters on header names, like the hop-by-hop and `Access-Control-*` lists; machines never see or set account cookies, and no code reads cookie values.
- `apps/server` reads its settings with `loadServerConfig(env)` (`src/lib/config.ts`). Accounts are on only when `DATABASE_URL` is set; then `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_URL` and `MAIL_FROM` are required, and the server exits at start-up if the database is unreachable or has pending migrations (`bun run db:migrate`). Tests build the config from an explicit env object, never `process.env`. Never log `DATABASE_URL`, `BETTER_AUTH_SECRET` or request headers.
- `apps/server` sends email only through the mailer (`src/modules/mailer/`): `createMailer({ transport, from })` is built in `index.ts` when accounts are on and passed to the modules that need it. Each email is one template file in `templates/` (`name` plus `render(data)` returning subject, text and HTML, with every value escaped in the HTML and no user input in the subject), listed in `templates/index.ts`, so `send` accepts only a known template with its own data. Tests use `createCaptureTransport()` from `mailer.testing.ts` (never imported by production code) and read links with `lastTo(address)`. Emails carry single-use links, so never log the link, a token, the recipient, the subject, the body or `SMTP_URL`; the mailer logs only the template name and `sent` or `failed (<code>)`, and keeps nodemailer's logger and debug output off. `bun apps/server/scripts/send-test-mail.ts <to>` sends a test `verifyEmail` to Mailpit.
- The host owns the shells (Bun's built-in PTY, so macOS/Linux only) and the layout state. State persists in `apps/host/.data/state.json` (gitignored); delete it to reset the layout.
- `apps/web/src/routeTree.gen.ts` is generated by TanStack Router. Never edit it by hand.
- New themes are added to the end of `packages/ui/src/themes.ts`.

## Skills

- Agent skills live in `.agents/skills/<name>/SKILL.md` (the Agent Skills format). Add new skills there, not in a tool-specific folder.
- Claude Code reads `.claude/skills/`, so each skill also needs a symlink: `ln -s ../../.agents/skills/<name> .claude/skills/<name>`.

## Repo etiquette

- Feature branches and PRs are preferred. Before committing on `main`, ask the user whether to commit there or create a branch.
- Commit messages are a single line unless a summary body is really needed (see the `commit` skill).
- `.temp/` is the user's personal scratch area. Ignore it, and don't edit it.
